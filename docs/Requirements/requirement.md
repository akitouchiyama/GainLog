# GainLog 要件定義書

## 1. 概要・背景・目的

GainLog は、日々の筋力トレーニング（種目・重量・回数・セット）を記録し、過去の記録を参照しながらトレーニングの成長を実感できることを目的とした個人向け Web アプリケーションである。

記録の入力負荷を下げるために前回記録した重量を自動表示する機能を持ち、月間・週間の記録を一覧できることで振り返りを容易にする。

## 2. 用語定義

| 用語 | 定義 |
|---|---|
| 種目（Exercise） | ベンチプレス、スクワットなど筋トレの種類 |
| セット（Set） | 1 種目内での実施単位。重量（kg）と回数の組で構成される |
| 記録（Workout Record） | ある 1 日に実施した種目・セットの集合 |
| メニュー（Menu） | 複数の種目・重量・回数・セット数をまとめて登録できるテンプレート（Phase 2） |

## 3. 想定利用者

- 開発者本人による個人利用を想定する（実質的に単一ユーザー）。
- クラウド上に公開するため、Google アカウントによる認証を必須とし、認証されたユーザーのみが自身の記録にアクセスできる。
- データモデル上はユーザー ID に紐づく設計とし、将来的な複数ユーザー対応の可能性は残すが、本要件のスコープには含めない（[非目標](#9-非目標スコープ外)参照）。

## 4. スコープ

### Phase 1（MVP）
- 筋トレ記録の作成・詳細表示・編集・削除
- 前回記録重量の自動表示
- 月間カレンダー表示
- 週間一覧表示
- 種目管理（事前定義リスト＋自由追加）
- Google アカウントによる認証
- レスポンシブ Web 対応

### Phase 2
- 成長を実感できる棒グラフ表示
- 1 種目20回以上達成時の重量アップ促進機能
- トレーニング目標設定機能（種目ごとの目標重量・回数に加え、体重など筋トレを続ける根本的な目標の設定と表示）
- 記録データのエクスポート機能
- メニュー機能（複数種目をまとめて一括登録できるテンプレート、CRUD対応）

## 5. 機能要件

### 5.1 筋トレ記録（作成・詳細表示・編集・削除）
- ユーザーは日付・種目・セットごとの重量（kg）と回数を入力し、1 日分の記録として保存できる。
- 1 日の記録には複数の種目を含めることができ、各種目には複数のセットを含めることができる。
- 保存済みの記録は詳細表示・編集・削除ができる。
- 記録の削除は、日単位（1 日分の記録全体）・種目単位（特定の日の特定種目をまるごと）・セット単位（特定の 1 セットのみ）のいずれの粒度でも行える。

### 5.2 前回記録重量の自動表示
- 記録の入力・編集画面において、同一種目・同一セット番号の直近の記録（重量・回数）を画面上部に表示する。
- 該当する過去記録が存在しない場合は、その旨がわかる表示とする（プレースホルダー等）。

### 5.3 月間カレンダー表示
- 月単位のカレンダー UI で、記録が存在する日を識別できるようにする。
- 日付をタップすると、その日の詳細記録画面へ遷移する。

### 5.4 週間一覧表示
- 直近 1 週間（当日を含む過去 7 日間のローリングウィンドウ）の記録を一覧表示する。
- 日付をタップすると、その日の詳細記録画面へ遷移する。

### 5.5 種目管理
- 代表的な種目（例：ベンチプレス、スクワット、デッドリフト等）を初期データとして事前定義する。
- ユーザーは独自の種目を自由に追加できる。
- 種目の編集は、ユーザーが追加した種目のみ可能とする（事前定義種目は編集不可）。
- 種目の削除は、ユーザーが追加した種目のみ可能とする（事前定義種目は削除不可）。ただし、既に記録で使用中の種目は削除できない（参照整合性の保護）。

### 5.6 認証
- Google アカウントによる OAuth 2.0 / OpenID Connect（OIDC）認証を導入する。
- 未認証のユーザーは記録の閲覧・操作ができない。
- ログインした Google アカウントに紐づく記録のみアクセス可能とする。
- 許可された Google アカウント（メールアドレス）以外はログインを拒否する（allowlist 方式）。許可対象の管理方法は別途設計で定める。

### 5.7（Phase 2）成長グラフ
- 種目ごとの重量推移を棒グラフで表示し、成長を実感できるようにする。
- 集計軸（日次／週次／月次）の詳細は Phase 2 着手時に別途検討する。

### 5.8（Phase 2）重量アップ促進機能
- 同一種目で 20 回以上のセットを達成した場合、次回の重量を上げることを促す表示を行う。
- 判定の対象（1 セットで 20 回以上か、合計回数か等）は Phase 2 着手時に別途検討する。

### 5.9（Phase 2）トレーニング目標設定機能
- 種目ごとの目標（重量・回数）、および体重など根本的なトレーニング目標を設定できるようにする。
- 詳細は Phase 2 着手時に別途検討する。

### 5.10（Phase 2）データエクスポート
- 記録データを CSV 等の形式でエクスポートできるようにする。
- 出力形式・対象範囲の詳細は Phase 2 着手時に別途検討する。

### 5.11（Phase 2）メニュー機能
- 複数の種目とそれぞれの重量・回数・セット数をまとめたメニューを作成・編集・削除（CRUD）できる。
- メニューを選択すると、含まれる種目・セットを一括で記録として登録できる。
- 代表的なメニューを初期データとして事前定義し、ユーザーは独自のメニューを自由に追加できる。
- メニューの編集・削除は、ユーザーが追加したメニューのみ可能とする（事前定義メニューは編集・削除不可）。
- 詳細は Phase 2 着手時に別途検討する。

## 6. 非機能要件

### 技術スタック
- **Backend**: TypeScript, Hono, Zod, OpenAPI, Valibot, Vitest
- **Frontend**: TypeScript, React, TailwindCSS, Valibot, Vitest, Storybook
- **DB**: Cloudflare D1（SQLite 互換）

### デプロイ
- Cloudflare Workers 上にデプロイし、任意の場所・端末からアクセス可能とする。
- フロントエンド（React SPA）は Workers Static Assets により、バックエンド（Hono API）・DB（D1）と同一 Cloudflare プロジェクトに同梱する。
- 選定理由: Hono は Cloudflare Workers ランタイムを公式に最も密接にサポートしており、実質 1 ユーザー・低トラフィックの利用規模であれば無料枠（Workers 10 万 req/日、D1 5GB storage 等）の範囲内で運用できる見込みのため。

### パフォーマンス目標
- 初回表示（First Contentful Paint 目安）: 3 秒以内
- API 応答時間: 500ms 以内（P95）
- Lighthouse Performance スコア: 80 以上

### 対応端末・レスポンシブ対応
- レスポンシブ Web として、スマートフォン・タブレット・PC のブラウザで問題なく閲覧・操作できること。
- 対応ブラウザ（各直近 2 バージョン）
  - PC: Chrome, Edge, Safari
  - モバイル: iOS Safari, Android Chrome
- ネイティブアプリ化は行わない（[非目標](#9-非目標スコープ外)参照）。

### 単位系
- 重量の単位は kg のみとする。lb 対応は行わない。

### 日付・タイムゾーン
- 日付の基準タイムゾーンは JST（Asia/Tokyo）に固定する。

### セキュリティ
- Google OAuth 2.0 / OIDC による認証を必須とし、認証されていないユーザーからのアクセスを拒否する。

## 7. データモデル概要

| エンティティ | 概要 |
|---|---|
| User | Google アカウントに紐づくユーザー情報 |
| Exercise（種目） | 名称、カテゴリ（任意）、事前定義／ユーザー追加の区分 |
| WorkoutRecord（1 日の記録） | 日付、ユーザー ID |
| WorkoutSet（セット記録） | 記録 ID、種目 ID、セット番号、重量（kg）、回数 |

※ 詳細なスキーマ設計は本要件定義書のスコープ外とし、別途設計ドキュメントで定める。

## 8. 受入条件

- ユーザーが Google アカウントでログインできる。
- ある日の筋トレ記録（種目・セットごとの重量・回数）を作成・保存できる。
- 保存した記録を詳細表示・編集・削除できる。
- 記録の入力・編集画面で、同一種目・同一セット番号の直近記録が上部に表示される。
- 月間カレンダーで記録のある日が識別でき、タップしてその日の詳細記録画面に遷移できる。
- 週間一覧で直近の記録を確認でき、タップしてその日の詳細記録画面に遷移できる。
- スマートフォンのブラウザで問題なく操作できる。

## 9. 非目標（スコープ外）

- 複数ユーザー間でのデータ共有・SNS 的機能
- ネイティブアプリ化（iOS / Android）
- kg 以外の単位（lb 等）への対応
- Phase 1 時点でのグラフ表示・重量アップ促進機能（Phase 2 とする）
- SAML 等エンタープライズ向け SSO 連携

## 10. 制約・前提・未決事項

- DB に Cloudflare D1（SQLite 互換）を採用するため、PostgreSQL 固有の機能（JSONB、高度な拡張機能等）は利用できない。将来的にそれらが必要になった場合は、Cloudflare Workers を維持したまま Neon（Serverless PostgreSQL）へ移行する選択肢がある。
- Phase 2 の重量アップ促進機能における判定ロジックの詳細は未定。Phase 2 着手時に検討する。
