# GainLog 共通仕様書

## 1. 概要

本書は、複数のAPIエンドポイント・画面をまたいで共通に適用される、以下4点の横断的な仕様を実装可能な粒度で定めるものである。

- 共通APIエラーレスポンス形式（2章）
- バリデーションエラー形式（3章）
- ロギング方針（4章）
- フロントエンド共通UI仕様（ローディング・エラー表示、5章）

対象読者は開発者本人（実装者）であり、実装時にそのまま参照できる粒度で記述する。

以下を前提とする。

- 性能効率性・可用性・バックアップ/DR等、一般的に「非機能要件」と呼ばれる事項（パフォーマンス目標・対応端末・単位系・日付タイムゾーン等）は要件定義書（`docs/Requirements/requirement.md`）6章で既に定義済みであり、本書はそれとは異なる、実装上の横断的な取り決め（Cross-cutting Concerns）を対象とする。本書では要件定義書6章の内容を繰り返さない。
- 認証・認可に関するエラーハンドリング（401/404の使い分け等）は認証設計書（`docs/Design/Basic/auth.md`）10章で定義済みであり、本書は認証・認可以外の一般的なAPIエラー形式を対象とする。
- OpenAPI設計書（`docs/Design/Basic/openapi.yaml`）に先行して定義されていた最小限のErrorスキーマ（`code`/`message`のみ）を、本書の内容に合わせて拡張する（7章「スコープ外」参照。openapi.yaml側の追従修正は別途行う）。

## 2. 共通APIエラーレスポンス形式

### エラーレスポンスの基本構造

全APIエンドポイントのエラーレスポンスは、以下の構造に統一する。

```json
{
  "code": "validation_error",
  "message": "入力内容に誤りがあります。",
  "fields": [
    { "field": "weightDeci", "message": "0以上999.9以下で入力してください。" }
  ]
}
```

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `code` | string | 必須 | 機械判定用のエラーコード。3章の対応表に定める値のいずれか |
| `message` | string | 必須 | 人間可読なエラーメッセージ（日本語。UIにそのまま表示可能な文言とする） |
| `fields` | array | 任意 | フィールド単位のエラー詳細。バリデーションエラー（`validation_error`）でのみ付与する。3章参照 |

### HTTPステータスコードと`code`値の対応表

`code`値はHTTPステータスコードと1対1で対応させる。

| HTTPステータス | `code`値 | 用途 |
|---|---|---|
| 400 Bad Request | `validation_error` | リクエストの形式・入力制約違反（3章参照） |
| 401 Unauthorized | `unauthorized` | 未認証（Cookieなし・期限切れ。auth.md 10章） |
| 403 Forbidden | `forbidden` | 事前定義データの編集・削除等、権限上許可されない操作（requirement.md 5.5、openapi.yaml） |
| 404 Not Found | `not_found` | 対象リソースが存在しない、または他ユーザー所有リソースである（auth.md 8章） |
| 409 Conflict | `conflict` | 一意制約違反（`set_number`重複）、参照整合性違反（使用中種目の削除）等 |
| 500 Internal Server Error | `internal_error` | サーバー内部エラー（想定外の例外） |

- `code`値をHTTPステータスと1対1にすることで、SPA側は`code`を見ずにHTTPステータスのみでも大枠のエラー種別を判定できる（`code`はUI側でのメッセージ出し分け・ログ突合等の補助情報として用いる）。
- 同一ステータス内でエラー要因が複数ありうる場合（例：409の「set_number重複」と「使用中種目の削除」）も、`code`はステータス単位の粒度に留め、詳細な要因は`message`（人間向け）で表現する。業務ごとに`code`を細分化しない方針とする（2026-08-23、対象範囲確認時に合意）。

## 3. バリデーションエラー形式

### `fields`配列の仕様

`code: "validation_error"`（400）のレスポンスでは、`fields`配列によりフィールド単位のエラー内容を返す。

| フィールド | 型 | 必須 | 説明 |
|---|---|---|---|
| `field` | string | 必須 | エラーが発生した入力フィールド名 |
| `message` | string | 必須 | 当該フィールドのエラーメッセージ（日本語） |

- `field`名は、openapi.yamlの各スキーマで定義されたプロパティ名（camelCase）をそのまま用いる。例：`weightDeci`（重量）、`reps`（回数）、`setNumber`（セット番号）、`name`（種目名）、`category`（カテゴリ）。
- 1リクエストに複数の入力制約違反が含まれる場合、`fields`配列に該当する全フィールドのエラーを含める（最初の1件で打ち切らない）。UI側は各入力欄の直下にインラインでエラーメッセージを表示できるようにするため。
- リクエストボディ自体が不正な形式（JSON構文エラー等、個別フィールドに紐付かないエラー）の場合は、`fields`を省略し`message`のみで表現する。

### API・UIでの適用範囲

- 重量・回数・セット番号の入力制約（requirement.md 5.1）は、APIバリデーション（サーバー側）・UI入力フォーム（クライアント側）の双方で同一のメッセージ文言を用いる（screens.md 5.5節・7章参照）。
- UI側での即時バリデーション（入力時・フォーカスアウト時等の実装詳細）は本書のスコープ外とし、フロントエンド実装時に定める。

## 4. ロギング方針

### ログレベルの定義・使い分け

Cloudflare Workersの標準出力（`console.log`等）を用い、以下4段階のログレベルを使い分ける。

| レベル | 用途 | 出力関数 |
|---|---|---|
| `debug` | 開発時のみ有効化する詳細トレース。本番では出力しない想定 | `console.debug` |
| `info` | 通常のリクエスト処理の要点（例：ログイン成功、記録の作成・削除等の主要な状態変化） | `console.info` |
| `warn` | 想定内だが注意を要する事象（例：バリデーションエラー、404・409等のクライアントエラー応答） | `console.warn` |
| `error` | サーバー内部エラー（500）、想定外の例外 | `console.error` |

- 本番環境では`debug`レベルの出力を行わない（コード上で出力しない、または将来的に環境変数等で制御する。具体的な制御方法は実装時に定める）。
- 認証関連の詳細なログ出力方針（何を・どのレベルで出力するか）はauth.md 10章に既に定義があり、本章の分類と整合させる（例：ID token検証失敗は`warn`、allowlist外アクセスは`warn`）。

### 構造化ログのフォーマット

ログはJSON形式の構造化ログとして出力する。

```json
{
  "level": "warn",
  "timestamp": "2026-08-23T12:00:00.000Z",
  "message": "validation_error: weightDeci out of range",
  "path": "/api/records/2026-08-20/exercises/{exerciseId}/sets",
  "method": "POST",
  "userId": "..."
}
```

| フィールド | 説明 |
|---|---|
| `level` | 上記4段階のいずれか |
| `timestamp` | ISO 8601形式（UTC） |
| `message` | ログメッセージ（英語可。PIIを含めない） |
| `path` / `method` | リクエストのパス・HTTPメソッド |
| `userId` | 認証済みリクエストの場合、内部ユーザーID（`users.id`）。**メールアドレス等のPIIは含めない** |

### PIIマスキング方針

PIIの取り扱いはauth.md 10章の方針をそのまま踏襲し、本書で重複定義しない。要点のみ再掲する。

- IDトークン・セッショントークン（生値・ハッシュ値問わず）・メールアドレス等のPIIは平文でログに出力しない。
- ユーザーの特定が必要な場合は、内部ユーザーID（`users.id`、非PII）を用いる。

## 5. フロントエンド共通UI仕様

画面固有の表示文言はscreens.md（5章・6章）で定義済みであり、本章では画面をまたいで共通利用するUIコンポーネントの振る舞いを定める。

### ローディング表示

| 状況 | 表示方針 |
|---|---|
| API通信中（一覧取得・詳細取得等） | 対象領域にスケルトン表示、またはスピナーを表示する。具体的なコンポーネント実装は実装時に定める |
| 更新系操作中（保存・削除等） | 操作対象のボタンを無効化し、ローディング状態を示す（連打による二重送信を防ぐ） |

### エラー表示（トースト）

| エラー種別 | 表示方針 |
|---|---|
| `validation_error`（400） | 個別の入力欄にインラインでエラーメッセージを表示する（3章の`fields`を利用）。トーストは表示しない |
| `unauthorized`（401） | グローバルに検知し、ログイン画面へ遷移する（auth.md 10章）。トーストは表示しない |
| `forbidden`（403）/`not_found`（404）/`conflict`（409） | トースト通知でエラーメッセージ（`message`）を表示する |
| `internal_error`（500）/ネットワークエラー | トースト通知で「通信エラーが発生しました。もう一度お試しください。」等の汎用メッセージを表示する（`message`をそのまま出さず、詳細を露出しない） |

- トーストの表示時間・アニメーション等の具体的な実装は実装時に定める（8章参照）。

## 7. スコープ外

以下は本設計書の対象外とする。

- トーストの具体的なアニメーション・表示時間・スタックの積み方等のUIコンポーネント実装詳細（実装時に定める）
- 本番環境でのログレベル制御の具体的な実装方法（環境変数分岐等。実装時に定める）
- Cloudflare Workers Logs / Logpush等、ログの外部転送・保管・監視基盤の構成（architecture.md 9章の通り、監視・アラート設計自体を本アプリでは導入しない）
- 画面固有のエラーメッセージ文言（`error`クエリパラメータの値ごとの表示等）は`screens.md`で定める
- レート制限・リトライ方針（要件定義書に該当要件がないため対象外）
