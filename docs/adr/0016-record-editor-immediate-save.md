# 0016. 記録画面は操作ごとの即時保存とする

- Status: Accepted
- Date: 2026-09-27

## Context

記録詳細・編集画面（`/records/:date`、`screens.md` 5.5）の保存方式を決める必要があった。`openapi.yaml`（基本設計で凍結済み）は、セット単位・種目ブロック単位・日単位の細かい CRUD エンドポイントのみを持ち、「1日分の変更をまとめて保存する」エンドポイントを持たない。

| 案 | 内容 | トレードオフ |
|---|---|---|
| **A. 操作ごとの即時保存（採用）** | セット追加・編集・削除、種目ブロック追加・削除等、それぞれの操作を都度 API へ送信する。編集モードは入力欄の見た目の切替のみ | API の粒度と一致し、部分失敗が起きない。画面全体の「保存」「キャンセル」を持てない（各操作が個別に確定する） |
| B. 編集内容をまとめて保存 | 編集モード中はローカルの状態のみ変更し、「保存」で差分を複数 API 呼び出しに分解して送信、「キャンセル」で破棄できる | 「保存」を UX として提供できるが、複数 API 呼び出しの一部だけが失敗した場合の再同期・部分適用状態の表示を設計する必要がある（D1 の batch() は複数 API リクエストをまたいで原子性を持たない。`backend.md` 7.1） |

## Decision

案 A（操作ごとの即時保存）を採用する。

- セット追加・セット編集・セット削除・種目ブロック追加・種目ブロック削除・日単位削除のそれぞれを、都度対応する API へ即座に送信する。
- 「編集モード」は入力欄を表示させる見た目の切替であり、値の変更操作自体はモードに関わらず即時に確定・送信される。「完了」ボタンは表示モードへ戻すのみで、追加の API 呼び出しを行わない。
- 記録が存在しない日は、最初から空の編集モードとして開始する（`GET /records/{date}` が `exercises: []` の200を返す。`backend.md` 8.8）。

詳細は `docs/Design/Detailed/frontend.md` 7.4章・7.5章。

## Consequences

- 各操作の成功/失敗が独立するため、途中失敗時の「一部だけ保存された」という曖昧な状態が生じない。失敗した操作だけを再試行すればよい。
- 画面全体の「保存」ボタンによる一括確定という一般的な UX は提供しない。ユーザーは各操作の完了を都度目にする（トースト・インラインエラーで結果を把握する。`frontend.md` 6章）。
- API 呼び出し回数が増える（セットを5つ追加すれば5回のリクエスト）。実質1ユーザー・低トラフィックの利用規模（`requirement.md` 3章）を踏まえ、パフォーマンス上の問題にはならないと判断する。
